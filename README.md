# IEEE-CIS Fraud Detection

ამ კონკურსის მთავარი მიზანი იყო დიდი დატასეტიდან ისეთი მოდელის გაწვრთნა, რომელიც განსაზღვრავდა, ტრანზაქცია ყალბია თუ არა. 
ეს არის კლასიფიკაციის ამოცანა, რომლის გადასაჭრელად ვცადე რამდენიმე სხვადასხვა მიდგომა: Logistic Regression, Decision Tree, Random Forest და XGBoost.

## Feature Engineering

### ცვლადების ამოღება
არარელევანტური feature-ები, როგორიც იყო `TransactionID` და ტრანზაქციის დრო (`TransactionDT`), ამოვიღე.

### გამოტოვებული მნიშვნელობები (NaN)
ცარიელი მნიშვნელობები მედიანით შევავსე.

## Feature Selection

Feature Selection-ისთვის გამოვიყენე რამდენიმე ძირითადი მიდგომა:

### კორელაციის ფილტრი
გავფილტრე ისეთი ცვლადები, რომლებიც ერთმანეთთან მაღალ კორელაციაში იყვნენ. Threshold-ის სხვადასხვა მნიშვნელობა ვცადე, თუმცა შედეგზე დიდად არ იმოქმედა.

### SHAP Values
XGBoost-ში გამოვიყენე SHAP Values feature-ების ასარჩევად, რამაც საკმაოდ გააუმჯობესა შედეგი.

თავიდან Baseline მოდელი დავატრენინგე პატარა დატასეტით, რომ გამეგო, რომელი feature-ები იყო ინფორმაციის მატარებელი და რომელი — არა. ავაგე გრაფიკები SHAP Value-ებისთვის.


![Feature Importance Plot](/plots/shap_importance.png)

![Beeswarm Plot](/plots/shap_plot.png)

გარკვეული Feature-ების ამოყრა მიუმჯობესებდა სქორს, მაგალითად: `M5`, `V294`, `V70`, `M4`. 
ისინი გრაფიკზე ძალიან მჭიდროდ იყვნენ განლაგებული (0-თან ძალიან ახლოს) და ზოგიერთ მათგანს დაბალი ვარიაცია ჰქონდა. 
ამიტომ, SHAP-ების გრაფიკების ნახვის შემდეგ, ეს Feature-ები ხელით ამოვყარე.

### NaN Threshold
გამოვიყენე ზღვარი იმ ცვლადების გადასაყრელად, რომლებსაც ძალიან ბევრი NaN მნიშვნელობა ჰქონდათ.

თავდაპირველად ეს მაჩვენებელი `0.7` ავიღე, რამაც ძალიან ბევრი ცვლადი გამიფილტრა, შეამცირა ინფორმაცია და საბოლოოდ უფრო ცუდი მოდელები მივიღე.

შემდეგ Threshold ავწიე `0.8 - 0.9` დიაპაზონში, რამაც შედეგები საგრძნობლად გააუმჯობესა.

## ტრენინგი

როგორც ზემოთ აღვნიშნე, დავტესტე ოთხი მოდელი. ტრენინგის პროცესში ხშირი პრობლემა იყო **Overfitting**. 
ბევრ მოდელს უკეთესი ვალიდაციის შედეგი ჰქონდა, მაგრამ ოვერფიტის გამო საბოლოოდ უფრო სტაბილური მოდელის არჩევა მიწევდა.

---

## ტექნიკური დეტალები და გამოწვევები

### მეხსიერების (RAM) პრობლემა
მონაცემების გაერთიანებისას Kaggle-ზე საკმაოდ დიდი RAM მოხმარება მქონდა. თავიდან Cross Validation-ს ვცდილობდი, მაგრამ RAM არ მყოფნიდა.

ამიტომ, ცალკე გამოვყავი ვალიდაციის სეტი (თავიდანვე ასე უნდა მექნა, რადგან მონაცემები ამის საშუალებას იძლეოდა). 
ასევე, ზედმეტი მეხსიერება რომ არ დაკავებულიყო, კოდში ვშლიდი იმ ცვლადებს, რომლებსაც აღარ ვიყენებდი.


### დაუბალანსებელი კლასები
გამოვიყენე **Undersampling**. მოდელები დავატრენინგე ისეთ ტრენინგ სეტზე, რომელსაც `30%` ჰქონდა `1`-იანები თარგეთში.

ამ შეფარდების ცვლილება შედეგს დიდად არ ცვლიდა (`50/50`-იც ვცადე და იგივე იყო), ამიტომ დავტოვე `30/70`.

ვალიდაციის და ტესტ სეტი, რა თქმა უნდა, ორიგინალი შეფარდებით დავტოვე.

## შეფასების მეტრიკა

მოდელების შესაფასებლად გამოვიყენე **ROC AUC**, რადგან Kaggle-იც ამას იყენებს და ამ შემთხვევაში ბევრად უფრო მნიშვნელოვანია, ვიდრე Accuracy.

დაუბალანსებელი დატასეტის გამო, მოდელმა სულ რომ `0`-ები (ან `1`-იანები) დააბრუნოს, მაინც მაღალი (~97%) Accuracy ექნება. 
ROC კი ამ პრობლემას აგვარებს და აფასებს, რეალურად რამდენად კარგად შეგვიძლია `0`-ების გარჩევა `1`-იანებისგან.

## ჰიპერპარამეტრების ოპტიმიზაცია

ყველა მოდელის ჰიპერპარამეტრების ოპტიმიზაციისთვის გამოვიყენე `GridSearch`.

თავდაპირველად ყველა შესაძლო კომბინაციას ვტესტავდი, თუმცა ეს ძალიან დიდ დროს მოითხოვდა. 
შემდეგ მიდგომა შევცვალე და შემთხვევითად ვირჩევდი 10 კონფიგურაციას, საიდანაც საუკეთესოს ვიტოვებდი.

## Logistic Regression

- **C (Inverse Regularization Strength):** რაც უფრო პატარაა ეს პარამეტრი, მით უფრო თანაბრად ანაწილებს მოდელი წონებს და არ ეყრდნობა ერთ კონკრეტულ feature-ს. დავტესტე `0.01`-დან `10`-მდე.
- **penalty:** დავტესტე `l1` და `l2`.  
  - `l1` სუსტ feature-ებს ანულებს  
  - `l2` ზოგადად ყველა წონას ამცირებს  

**საუკეთესო პარამეტრები:**  
- `penalty = l1`  
- `C = 0.01`

---

## Decision Tree

- **max_depth:** ხის სიღრმის შეზღუდვა  
- **min_samples_split / min_samples_leaf:** ხის შეზღუდვა, რომ split გააკეთოს მხოლოდ მაშინ, თუ საკმარისი რაოდენობის ინფორმაცია (data) აქვს  
- **class_weight:** ავიღე `balanced`, რადგან ამ შემთხვევაში მოდელი უფრო დიდ ყურადღებას აქცევს minority კლასს  

**საუკეთესო პარამეტრები:**  
- `max_depth = 10`  
- `min_samples_split = 100`  
- `min_samples_leaf = 25`  

ეს პარამეტრები იმდენად კარგად შეირჩა, რომ Overfitting-ის პრობლემა არ მქონია და საუკეთესო ვალიდაციის მოდელი პირდაპირ საუკეთესო აღმოჩნდა.

---

## Random Forest

აქაც ზუსტად იგივე ჰიპერპარამეტრები გვაქვს, რაც Decision Tree-ში, რადგან ბევრ ხეს ვატრენინგებთ. ემატება მხოლოდ ხეების რაოდენობა:

- **n_estimators:** ხეების რაოდენობა  

**საუკეთესო პარამეტრები:**  
- `max_depth = 16`  
- `min_samples_leaf = 25`  
- `min_samples_split = 50`  
- `n_estimators = 100`

---

## XGBoost

- **learning_rate / n_estimators:** აიძულებს მოდელს, რომ ნელ-ნელა ისწავლოს.  
  - `learning_rate` ზღუდავს თითოეული ხის მნიშვნელობას  
  - `n_estimators` ხეების რაოდენობაა  

- **gamma:** რეგულარიზაციის პარამეტრი — მოდელი split-ს აკეთებს მხოლოდ მაშინ, თუ ის საგრძნობლად გვიუმჯობესებს შედეგს  
- **min_child_weight:** `gamma`-ს მსგავსად, გვიცავს ოვერფიტისგან  
- **subsample / colsample_bytree:** ვაიძულებთ ყველა ხეს, ისწავლოს random რაოდენობის row-ები და column-ები (ფაქტობრივად Bootstrapping)

**საუკეთესო პარამეტრები:**  
- `learning_rate = 0.05`  
- `n_estimators = 400`  
- `max_depth = 5`  
- `min_child_weight = 5`  
- `gamma = 2`  
- `subsample = 0.8`  
- `colsample_bytree = 0.8`
